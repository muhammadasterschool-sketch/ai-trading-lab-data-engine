## PART 1: RESOLUTION OF ALL 15 UNRESOLVED QUESTIONS

### UQ-01: Should `periods_per_year` be a per-instrument property or a calendar property?

**Selected Option:** Option A — Make `periods_per_year` a property of `CalendarRef`.

**Final Rationale:** The `periods_per_year` dict in `src/data_engine/strategy/metrics.py` currently hardcodes values assuming 24/7 trading (M1=525600, D1=365). This is correct for crypto and FX but wrong for equities (NYSE has ~252 trading days) and futures (exchange-specific). `Timeframe` describes data granularity, not market availability. These are distinct concepts and must be decoupled. The `CalendarRef` model owns the trading schedule and therefore owns `periods_per_year`. Default values for 24/7 markets (crypto, FX) are inherited by calendar definitions, but can be overridden per-instrument. The `metrics.py` `periods_per_year` dict becomes the default for calendars that do not specify a custom value.

**Dependencies:** Calendar interface design (UQ-05), CalendarRef model.

**Affects:** Later Phase 4A phases (multi-asset metrics).

**NON-BLOCKING FOR PHASE 4A.1** — Phase 4A.1's temporal model does not use `periods_per_year`. The existing `metrics.py` dict remains unchanged.

### UQ-02: How should the `PitSidecar` be versioned independently of the dataset?

**Selected Option:** Option B (immutable sidecars) combined with Option C elements (backward-compatible defaults).

**Final Rationale:** `PitSidecar` is immutable once created — it records the temporal metadata snapshot for a specific dataset version. If the schema evolves, a new `PitSidecar` is created for the new dataset version; the old sidecar remains valid for its original dataset. Legacy Phase 3 datasets without a sidecar receive a default `PitSidecar` where `event_time = observation_time = publication_time = effective_time = revision_time = dataset.provenance.retrieval_timestamp`, `ingestion_time = datetime.now(UTC)`, and `MissingFieldPolicy = REJECT` for `event_time`. This default sidecar is generated by `PitViewBuilder` on first access and cached.

**Dependencies:** PitSidecar model, PitViewBuilder, default sidecar generation logic.

**Affects:** Phase 4A.1 (PIT view construction).

---

### UQ-03: Should `PitView` be constructed before or after the backtest engine runs?

**Selected Option:** Option A — `PitViewBuilder` constructs a filtered `Dataset` before `BacktestEngine.run()`.

**Final Rationale:** Adding `pit_cutoff` or `PitView` to `BacktestConfig` would change its canonical serialization, which changes `config_hash`, which changes `result_hash`. This violates DD-14 (`BacktestProvenance.compute_result_hash()` is never modified). By constructing the PIT-filtered dataset beforehand, the backtest engine receives an unfiltered `Dataset` and `BacktestConfig` remains byte-identical. The pipeline is: `Dataset → PitViewBuilder.filter(dataset, pit_cutoff) → PIT-filtered Dataset → BacktestEngine.run(strategy, filtered_dataset)`. The existing `BacktestEngine.run(strategy, dataset)` signature is preserved exactly.

**Dependencies:** PitViewBuilder, PitSidecar, PitCutoff model.

**Affects:** Later Phase 4A phases (PIT-aware research workflows).

**NON-BLOCKING FOR PHASE 4A.1** — Phase 4A.1 does not interact with `BacktestEngine`.

### UQ-04: How are `ApprovalMetadata` decisions represented?

**Selected Option:** Option B (hash commitment) combined with Option C (external audit reference).

**Final Rationale:** Approval must be both programmatically verifiable and human-auditable. A hash commitment (`sha256(research_contract | config_hash | dataset_hash | pit_view_hash)`) provides deterministic, immutable proof that a specific set of inputs was approved. An external audit record provides the human-readable context (approver identity, timestamp, scope). The `ApprovalMetadata` model contains: `approval_hash: str`, `approver: str`, `timestamp: datetime`, `scope: str`, `external_reference: Optional[str]`. The `ResearchContract` validates that the current experiment inputs match the approved hash before allowing research to proceed.

**Dependencies:** ResearchContract model, ApprovalMetadata model, hash computation.

**Affects:** Later Phase 4A phases (research governance).

**NON-BLOCKING FOR PHASE 4A.1** — Data quality checks are sufficient for Phase 4A.1.

### UQ-05: Should the `CalendarInterface` be a Pydantic model or a protocol/ABC?

**Selected Option:** Option C — Both Pydantic model and protocol.

**Final Rationale:** The codebase consistently uses Pydantic models for all domain entities, so configuration and serialization must be Pydantic. However, the runtime calendar interface (`is_trading_day()`, `get_session_hours()`) may need provider-specific implementations that are not Pydantic models. The pattern: `CalendarRef` (Pydantic model for configuration) references a `calendar_id` and `calendar_version`. A `CalendarRegistry` resolves the `calendar_id` to a concrete implementation that satisfies the `CalendarInterface` protocol. This follows the existing `ProviderFactory` pattern for `MarketDataProvider`.

**Dependencies:** CalendarRef, CalendarRegistry, CalendarInterface protocol.

**Affects:** Later Phase 4A phases (calendar infrastructure).

**NON-BLOCKING FOR PHASE 4A.1** — Phase 4A.1's temporal model does not use a calendar interface.

### UQ-06: How does the `RolloverPolicy` handle ambiguous roll dates?

**Selected Option:** Option C (configurable policy) with Option A (fixed trading days) as default.

**Final Rationale:** The policy must be declarative and deterministic. The `RolloverPolicy` model serializes as: `roll_strategy|parameter`. Default: `fixed_trading_days|5` meaning roll 5 trading days before expiry. Alternative: `volume_shift|threshold`. The policy must be included in the `view_hash` and `experiment_id` because changing the roll policy produces different backtest results. Roll decisions must use only information available at the PIT cutoff (no look-ahead on volume data).

**Dependencies:** FuturesContract model, ContinuousSeries model, view_hash computation.

**Affects:** Later Phase 4A phases (futures research).

**NON-BLOCKING FOR PHASE 4A.1** — Phase 4A.1 does not handle futures.

---

### UQ-07: Should `TemporalContract` support asset-class-specific required fields?

**Selected Option:** Option C — `TemporalContract` has a `data_type` field that determines defaults, overridable.

**Final Rationale:** The existing `TemporalContract` has a `data_type: TemporalDataType` field and `required_fields`/`eligible_fields`/`non_eligible_fields` lists, but defaults are empty. The enhancement: `TemporalContract` constructor populates defaults based on `data_type`. `TemporalDataType.OHLCV` defaults to `required_fields=["event_time", "observation_time"]`, `eligible_fields=["publication_time", "effective_time", "revision_time"]`. `TemporalDataType.ECONOMIC` defaults to `required_fields=["event_time"]`, `eligible_fields=["publication_time", "effective_time"]` (publication_time may be null). `TemporalDataType.DERIVED` defaults to `required_fields=["event_time", "observation_time"]`, with `publication_time` allowed null. Users can override per-instance.

**Dependencies:** TemporalContract enhancement, TemporalDataType enum extension.

**Affects:** Phase 4A.1 (extended TemporalContract) and later phases.

### UQ-08: What is the relationship between `data_engine.pit` (v4.1.0) and proposed `data_engine.multi_asset.temporal`?

**Selected Option:** Option A — `multi_asset.temporal` extends `pit/temporal.py`, keeping both modules.

**Final Rationale:** The `pit/` module (`__version__ = "4.1.0"`) is written, tested (97 tests), and self-contained. It contains the foundational temporal model, availability policies, serialization, and hashing. Absorbing it would require rewriting all imports and potentially breaking the existing test structure. `multi_asset.temporal` imports from `data_engine.pit` and adds PIT-aware research constructs (`PitView`, `PitSidecar`, `RevisionHistory`, `PitViewBuilder`). This follows the established module separation pattern (`data_engine.quant` v2.0.0, `data_engine.strategy` v3.0.0, `data_engine.pit` v4.1.0).

**Dependencies:** Module import structure, version management.

**Affects:** Phase 4A.1 (module organization).

### UQ-09: How are timezone conversions handled when source timezone is unknown?

**Selected Option:** Option C (infer from venue metadata) with Option A (reject) as fallback.

**Final Rationale:** The `Venue` model will include a `timezone: str` field. The `DataIngester` requires the provider to specify the exchange timezone via `ProviderConfig.timezone`. If the provider does not specify it, ingestion raises `ValidationError`. Data with timezone-naive timestamps is rejected at `TemporalSemantics` validation time (already implemented in `pit/temporal.py`). The source timezone is preserved as metadata on the `Venue` model, not embedded in the UTC-normalized timestamp.

**Dependencies:** Venue model, ProviderConfig, DataIngester enhancement.

**Affects:** Phase 4A.1 (timezone handling) and later phases.

### UQ-10: Should `event_time` be required for all data types, including derived indicators?

**Selected Option:** Option A — `event_time` = timestamp of the bar the indicator is computed for.

**Final Rationale:** An EMA value computed for the 09:00 bar represents the market state at 09:00, not at the computation time. Using computation time creates misleading PIT views where indicators appear available later than they actually are. For derived indicators: `event_time` = bar timestamp (required), `observation_time` = computation completion time, `publication_time` may be null (synchronous computation) or the time the result was made available. `TemporalContract` for `TemporalDataType.DERIVED` sets `MissingFieldPolicy.ALLOW_NULL` for `publication_time`.

**Dependencies:** TemporalContract DERIVED policy, derived indicator temporal semantics.

**Affects:** Later Phase 4A phases (derived indicators).

**NON-BLOCKING FOR PHASE 4A.1** — Phase 4A.1 does not implement derived indicators.

---

### UQ-11: How does the `ResearchContract` handle partial approval?

**Selected Option:** Option B — Approval has scopes (data_approved, methodology_approved, results_approved).

**Final Rationale:** Research projects have distinct stages. A `ResearchContract` model has a `scopes` field: `Dict[str, ApprovalStatus]` where `ApprovalStatus` is {PENDING, APPROVED, REJECTED}. Each scope is independently approved with its own timestamp and approver. The `ApprovalMetadata` model records all scope approvals. A contract is considered fully approved only when all required scopes are APPROVED. This allows staged research workflows without compromising auditability.

**Dependencies:** ResearchContract model, ApprovalMetadata model, scope-based approval.

**Affects:** Later Phase 4A phases (research governance).

**NON-BLOCKING FOR PHASE 4A.1** — Phase 4A.1 uses `DataQualityGate` for data validation.

### UQ-12: Should `view_hash` include the tie-breaker policy?

**Selected Option:** Option A — Yes, `view_hash` includes the tie-breaker policy.

**Final Rationale:** The tie-breaker policy determines ordering of equal-time observations, which directly affects trade sequence and therefore backtest results. Two PIT views with the same cutoff and data but different tie-breakers produce different backtest results. The `view_hash` formula is: `sha256(pit_cutoff | revision_policy | instrument_spec_version | calendar_version | dataset_hash | temporal_filter | tie_breaker_policy)`. Changing any component creates a different `view_hash` and therefore a different `experiment_id`.

**Dependencies:** TieBreakerPolicy model, view_hash computation, experiment_id computation.

**Affects:** Phase 4A.1 (experiment identity) and later phases.

### UQ-13: How should `TemporalContract` handle `TemporalDataType.DERIVED`?

**Selected Option:** Option A — `publication_time` = computation completion time, with `MissingFieldPolicy.ALLOW_NULL` for DERIVED.

**Final Rationale:** Derived indicators are computed from raw data. The computation completion time is when the indicator becomes available. For synchronous computation, `publication_time` equals `observation_time`. For asynchronous computation, `publication_time` is later. The `TemporalContract` for `TemporalDataType.DERIVED` sets `required_fields=["event_time", "observation_time"]`, `eligible_fields=["publication_time", "effective_time", "revision_time"]`, and `missing_field_policy = ALLOW_NULL` for `publication_time`.

**Dependencies:** TemporalContract DERIVED policy, derived indicator temporal semantics.

**Affects:** Later Phase 4A phases (derived indicators).

**NON-BLOCKING FOR PHASE 4A.1** — Phase 4A.1 does not implement derived indicators.

---

### UQ-14: What is the interaction between `DataQualityGate` and `PitViewValidator`?

**Selected Option:** Option A — `PitViewValidator` runs after `DataQualityGate`.

**Final Rationale:** The pipeline is: `Dataset → DataQualityGate.check() → PitViewValidator.validate() → PIT-filtered Dataset`. `DataQualityGate` validates data quality (OHLC validity, NaN/Inf, volume semantics, evidence provenance). `PitViewValidator` validates temporal eligibility (publication_time <= pit_cutoff, effective_time <= pit_cutoff, revision_time <= pit_cutoff). Separating these concerns keeps each gate focused. `DataQualityGate` answers "Is this data valid?" and `PitViewValidator` answers "Is this data available at the PIT cutoff?" `DataQualityGate` is unchanged (existing Phase 3 component). `PitViewValidator` is a new component.

**Dependencies:** PitViewValidator model, DataQualityGate (existing, unchanged).

**Affects:** Phase 4A.1 (PIT validation) and later phases.

---

### UQ-15: Should `BacktestConfig` be extended with `pit_cutoff` or should `PitView` be constructed separately?

**Selected Option:** Option B — `PitView` is a separate pre-processing step.

**Final Rationale:** Adding `pit_cutoff` to `BacktestConfig` changes its canonical serialization, which changes `config_hash`, which changes `result_hash`. This violates DD-14. The `BacktestConfig` model is frozen with serialized string fields — adding a new field requires modifying the model, changing `model_dump_json()` output. By constructing `PitView` separately, the backtest engine receives a pre-filtered `Dataset` and `BacktestConfig` remains byte-identical. The pipeline is: `Dataset → PitViewBuilder.filter(dataset, pit_cutoff) → PIT-filtered Dataset → BacktestEngine.run(strategy, filtered_dataset)`. The existing `BacktestEngine.run(strategy, dataset)` signature is preserved.

**Dependencies:** PitViewBuilder, PitSidecar, PitCutoff model.

**Affects:** Later Phase 4A phases (PIT-aware research workflows).

**NON-BLOCKING FOR PHASE 4A.1** — Phase 4A.1 does not interact with `BacktestEngine`.

| DD-01 | PIT metadata lives in sidecar records, not in existing Phase 3 models | **FINAL** | `Candle`, `Instrument`, `Dataset`, `BacktestConfig`, `StrategySpec`, `BacktestProvenance` are NOT modified. All PIT metadata is stored in `PitSidecar` referenced by `dataset_id` + `dataset_version`. |

| DD-03 | Future publication is normally excluded, not an error | **FINAL** | `PitViewBuilder.filter()` excludes data where `publication_time > pit_cutoff` or `effective_time > pit_cutoff` silently. No error is raised. Future data is not an error condition — it is simply not yet available. |
| DD-04 | Calendar version is included in experiment identity | **FINAL** | `experiment_id = sha256(strategy_hash | view_hash | config_hash | feature_hash | tie_breaker_policy | code_version)` where `view_hash = sha256(pit_cutoff | revision_policy | instrument_spec_version | calendar_version | dataset_hash | temporal_filter | tie_breaker_policy)`. | DD-05 | Revision history is an append-only chain | **FINAL** | `RevisionChain` is immutable once created. Each revision references the previous revision's hash. |
| DD-06 | Deterministic tie-breakers are declared per experiment | **FINAL** | `TieBreakerPolicy` is declared in `PitExperimentConfig` and included in `view_hash`. Default: `venue|instrument_identity|data_source.source_id|canonical_bytes`. Insertion order is NEVER a tie-breaker. |
| DD-07 | Single latest-value record is NOT sufficient for PIT reconstruction | **FINAL** | Every data item in a `PitSidecar` has a `RevisionChain`. `PitViewBuilder` queries the revision chain, not just the latest value. A dataset with only a latest-value record cannot support PIT views at historical cutoffs. |
| DD-08 | `ingestion_time` is metadata-only, excluded from eligibility and hashes | **FINAL** — Already implemented in `pit/temporal.py`. | `TemporalSemantics.temporal_hash_input()` excludes `ingestion_time`. `TemporalContract` marks `ingestion_time` as `non_eligible`. |
| DD-09 | All PIT timestamps must be UTC-normalized, naive datetimes rejected | **FINAL** — Already implemented in `pit/temporal.py`. | `TemporalSemantics` validator rejects naive datetimes and normalizes all timestamps to UTC via `.astimezone(UTC)`. |
| DD-10 | Corporate actions create new instrument identity events, not data corrections | **FINAL** | Corporate actions (splits, dividends, symbol changes) create new `InstrumentSpecification` versions effective from the action date. Historical data remains under the old specification. Adjusted prices are a separate data product. |
| DD-11 | Futures continuous series and individual contracts are distinct instruments | **FINAL** | `FuturesContract` (dated, individual) and `ContinuousSeries` (back-adjusted/forward-adjusted) are distinct instrument types. They have separate identities and are never confused. |
| DD-12 | Calendar data is versioned and included in experiment identity | **FINAL** | `CalendarRef` has `calendar_id` and `calendar_version`. Calendar changes create new calendar versions. Calendar version is part of `view_hash` and `experiment_id`. |
| DD-13 | No wall-clock defaults in new deterministic schemas | **FINAL** | All new PIT-related Pydantic models must not use `default_factory=_now_utc` or any wall-clock default. All datetime fields must be explicitly provided or use `Field(default=None)`. Exception: `Candle.provider_timestamp` is a pre-existing Phase 3 model and must remain frozen (documented deviation). |
| DD-14 | `BacktestProvenance.compute_result_hash()` is never modified | **FINAL** | The `compute_result_hash()` method signature, formula, and implementation are unchanged. New PIT-aware hashes (`compute_view_hash()`, `compute_experiment_id()`) use new method names. Existing `result_hash` field continues to use the same formula. |
| DD-15 | Approval is represented as auditable external metadata | **FINAL** | `ApprovalMetadata` is an external record, not a method call on a gate. Approval is stored as a signed/commitment record with `approval_hash`, `approver`, `timestamp`, `scope`, `external_reference`. `DataQualityGate` remains unchanged. |
| DD-16 | Synthetic/simulated data must be explicitly labeled in PIT views | **FINAL** | Every `PitView` carries an `evidence_provenance` field (REAL, SYNTHETIC, SIMULATED, UNKNOWN). `PitViewBuilder` propagates evidence provenance from the underlying dataset. SYNTHETIC and SIMULATED data must never be represented as REAL market evidence. |

### 5.3 Extensibility Mechanism

New asset classes are added by:
1. Adding a new `AssetClass` enum value to the existing `AssetClass` enum (if needed)
2. Creating an asset-specific module under `multi_asset/<asset_class>/`
3. Implementing asset-specific instrument specifications that extend the shared `InstrumentSpecification`
4. Defining asset-specific `TemporalContract` defaults
5. Registering the asset class in the `AssetRegistry`
6. No modification to shared core is required — the core is asset-class-agnostic

### 6.1 Final Temporal Field Definitions

| Field | Definition | Required? | Participates in PIT Eligibility? | Participates in Hashes? |
|-------|-----------|-----------|----------------------------------|------------------------|
| `event_time` | When the market event actually occurred | Yes (for all non-derived types) | Yes | Yes |
| `observation_time` | When the observation was recorded | Yes | Yes | Yes |
| `publication_time` | When data was published/made available | Conditionally (governed by TemporalContract) | Yes — critical for PIT | Yes |
| `effective_time` | When data becomes effective/applicable | Conditionally | Yes | Yes |
| `revision_time` | When this specific version was revised | Conditionally (null for first revision) | Yes | Yes |
| `ingestion_time` | When data was ingested into the system | No (metadata-only) | **No** | **No** |
| `PIT cutoff` | The temporal boundary for the research view | Yes (per experiment) | Defines boundary | Yes (in view_hash) |
| `simulation start` | When the backtest simulation begins | No (backtest config) | No | Yes (in config_hash) |
| `simulation end` | When the backtest simulation ends | No (backtest config) | No | Yes (in config_hash) |

### 6.2 Critical Distinctions

**PIT cutoff ≠ Simulation end date.** The PIT cutoff answers "What information was publicly available as of time T?" The simulation end date answers "At which bar does the backtest stop?" A backtest can run from 2020-01-01 to 2023-12-31 with a PIT cutoff of 2023-12-31. Data published on 2024-01-15 that retroactively affects 2023 data is NOT visible in the PIT view.

**Stale ≠ Historical.** A data item with `revision_time = T1` that was later revised at `T2` is NOT stale — it is the correct data for any PIT view with `cutoff < T2`. It is only stale for PIT views with `cutoff >= T2`.

### 6.3 Eligibility Rules

A data item is **eligible** for a PIT view at cutoff `T` if and only if ALL of the following hold:
1. `event_time <= T`
2. `publication_time is None` OR `publication_time <= T`
3. `effective_time is None` OR `effective_time <= T`
4. `revision_time is None` OR `revision_time <= T`

A data item is **excluded** (not an error) if any condition fails. Future publication is silently excluded, not flagged as an error (DD-03).

### 6.4 Missing Metadata Policy

| Field | Default Policy | Behavior |
|-------|---------------|----------|
| `event_time` | REJECT | Missing `event_time` → ValidationError |
| `observation_time` | REJECT | Missing `observation_time` → ValidationError |
| `publication_time` | ALLOW_NULL (configurable) | Missing → excluded from eligibility check, treated as `publication_time = event_time` |
| `effective_time` | ALLOW_NULL | Missing → treated as `effective_time = event_time` |
| `revision_time` | ALLOW_NULL | Missing → treated as first revision (null) |
| `ingestion_time` | ALLOW_NULL | Always recorded, never affects eligibility or hashes |

### 6.5 Future Publication Handling

Data published after the PIT cutoff is **silently excluded** from the PIT view. This is not an error condition — it is the expected behavior of a time-sliced view. `PitViewBuilder.filter()` returns only eligible data items without raising errors for excluded items.

### 6.6 Revision Reconstruction

Each data item has a `RevisionChain` — an append-only list of `RevisionEntry` objects. Each entry has: `revision_time`, `publication_time`, `effective_time`, `data_hash`, `change_description`, `supersedes` (optional). At PIT cutoff `T`, only revisions with `revision_time <= T` are visible. The latest visible revision is the current value.

### 6.7 Duplicate Observations and Equal Timestamps

When two or more observations have identical `event_time`, `publication_time`, `effective_time`, and `revision_time`, the ordering is determined by the declared `TieBreakerPolicy`. The default tie-breaker priority is: `venue | instrument_identity | data_source.source_id | canonical_bytes`. Insertion order is NEVER a tie-breaker (DD-06).

### 6.8 Deterministic Tie-Breaking

All tie-breakers must produce identical output across all platforms and Python versions. The tie-breaker policy is included in `view_hash` (DD-12, UQ-12). Changing the tie-breaker policy creates a different experiment identity.

### 6.9 Wall-Clock Contamination

No wall-clock time may affect research identity or reproducibility. All datetime fields must be explicitly provided. The only exception is `Candle.provider_timestamp` which has `default_factory=_now_utc)` in the existing Phase 3 model — this is a pre-existing legacy exception documented as a known deviation (RC-01) and must NOT be modified (DD-13).

## PART 7: PIT VIEW CONTRACT

### 7.1 Final Pipeline Architecture

```
Raw/Processed Dataset
    ↓
TemporalMetadata (PitSidecar attached by dataset_id + dataset_version)
    ↓
PitViewValidator.validate(dataset, pit_cutoff)
    ↓ (passes/fails quality + temporal checks)
PitViewBuilder.filter(dataset, pit_cutoff, pit_sidecar)
    ↓ (returns PIT-filtered Dataset)
Immutable PIT Dataset/View (frozen)
    ↓
BacktestEngine.run(strategy, pit_filtered_dataset)
    ↓ (existing Phase 3 interface, unchanged)
BacktestResult (with view_hash, experiment_id added)
```

### 7.2 `BacktestEngine` Interface Preservation

The existing `BacktestEngine.run(strategy, dataset)` signature is **preserved exactly**. No modification to `BacktestEngine`, `BacktestConfig`, or `BacktestResult` is required for PIT functionality. `PitViewBuilder` produces a filtered `Dataset` which is passed to the existing `BacktestEngine.run()` method.

### 7.3 `BacktestProvenance.compute_result_hash()` Invariance

**DO NOT MODIFY `BacktestProvenance.compute_result_hash()`.**

The method signature, formula, and implementation are unchanged. The result_hash continues to be:
```
result_hash = sha256(strategy_hash|dataset_hash|canonical_trades|canonical_equity|canonical_metrics|config_hash)
```

New PIT-aware hashes use new method names:
- `compute_view_hash()` — computes `view_hash` from PIT view configuration
- `compute_experiment_id()` — computes `experiment_id` from all experiment inputs

New fields on `BacktestProvenance` are optional with defaults:
- `view_hash: str = ""`
- `experiment_id: str = ""`
- `pit_cutoff: Optional[datetime] = None`
- `hash_algorithm_version: str = "4.0.0"`

### 7.4 Additive/Versioned Integration

PIT functionality is **additive**. Legacy Phase 3 datasets without `PitSidecar` records are valid and usable. They are treated as having implicit temporal metadata (`event_time = observation_time = publication_time = effective_time = revision_time = provenance.retrieval_timestamp`). The `PitViewBuilder` generates a default `PitSidecar` on first access for legacy datasets.

## PART 8: EXPERIMENT IDENTITY

### 8.1 Final `experiment_id` Formula

```
experiment_id = sha256(strategy_hash | view_hash | config_hash | feature_hash | tie_breaker_policy | code_version)
```

Where:
- `strategy_hash` = `StrategySpec.to_hash()` (existing, unchanged)
- `view_hash` = `sha256(pit_cutoff | revision_policy | instrument_spec_version | calendar_version | dataset_hash | temporal_filter | tie_breaker_policy)`
- `config_hash` = `BacktestConfig._compute_config_hash()` (existing, unchanged)
- `feature_hash` = SHA-256 of all indicator definitions used (new)
- `tie_breaker_policy` = canonical serialization of `TieBreakerPolicy` (new)
- `code_version` = `engine_version` + `quant_engine_version` + `pit_module_version` (new)

### 8.2 Fields Affecting Deterministic Identity

The following fields **must** be included in `experiment_id`:

| Field | Source | Affects Identity? | Audit-Only? |
|-------|--------|-------------------|-------------|
| Strategy hash | `StrategySpec.to_hash()` | Yes | No |
| Dataset hash | `Dataset.raw_data_hash` or provenance hash | Yes | No |
| PIT view hash | `PitView.view_hash` | Yes | No |
| PIT cutoff | `PitView.pit_cutoff` | Yes | No |
| Revision policy | `RevisionPolicy` config | Yes | No |
| Instrument spec version | `InstrumentSpecification` version | Yes | No |
| Calendar version | `CalendarRef.calendar_version` | Yes | No |
| Feature definition hash | Hash of indicator definitions | Yes | No |
| Configuration hash | `BacktestConfig._compute_config_hash()` | Yes | No |
| Tie-breaker policy | `TieBreakerPolicy` config | Yes | No |
| Code/schema version | `engine_version`, `quant_engine_version`, `pit_module_version` | Yes | No |
| Run timestamp | `datetime.now(UTC)` | **No** | Yes (audit only) |
| Approver identity | `ApprovalMetadata.approver` | **No** | Yes (audit only) |
| Approval hash | `ApprovalMetadata.approval_hash` | **No** | Yes (audit only) |

### 8.3 Audit-Only Fields

The following fields are recorded for audit purposes but do NOT affect `experiment_id`:
- `run_timestamp` — when the experiment was run
- `approver` — who approved the research contract
- `approval_hash` — the approval commitment
- `approval_timestamp` — when approval was granted

### 8.4 Versioning Rules for Experiment Identity

Any change to any field in `experiment_id` creates a new experiment identity. This means:
- Changing the PIT cutoff → new `experiment_id`
- Changing the calendar version → new `experiment_id`
- Changing the tie-breaker policy → new `experiment_id`
- Changing the strategy → new `experiment_id`
- Changing the dataset → new `experiment_id`

This ensures that different PIT views over the same dataset always produce different experiment identities.

## PART 9: IMMUTABILITY AND VERSIONING

### 9.1 Immutable Boundaries

| Artifact | Immutability Rule | Versioning Mechanism |
|----------|-------------------|---------------------|
| Temporal metadata | Immutable once recorded in `TemporalSemantics` | Append-only revision chain |
| PIT sidecars | Immutable once created | New sidecar for new dataset version |
| PIT views | Immutable once constructed | New `PitView` for new cutoff/policy |
| Calendar definitions | Immutable once registered | New `CalendarVersion` for changes |
| Instrument specifications | Immutable per effective period | New `InstrumentSpecification` for changes |
| Dataset versions | Immutable after ingestion | New `DatasetVersion` for new ingestion |
| Experiment identity | Immutable once computed | New `experiment_id` for any change |
| Backtest results | Immutable after completion | New `BacktestResult` for new run |
| Revision chains | Append-only | New `RevisionEntry` appended |

### 9.2 How Changes Create New Versions

1. **Temporal metadata change** → New `RevisionEntry` appended to `RevisionChain`. Old revisions remain accessible.
2. **PIT sidecar change** → New `PitSidecar` created for new dataset version. Old sidecar remains valid for old dataset version.
3. **PIT view change** → New `PitView` constructed with new cutoff/policy. Old `PitView` remains valid for its cutoff.
4. **Calendar change** → New `CalendarVersion` created. Old calendar version remains valid for experiments using it.
5. **Instrument specification change** → New `InstrumentSpecification` effective from change date. Old specification remains valid for its effective period.
6. **Dataset change** → New `DatasetVersion` created. Old dataset version remains immutable and accessible.
7. **Experiment identity change** → New `experiment_id` computed. Old experiment identity remains valid for its inputs.

### 9.3 Version Propagation

When any component version changes, the change propagates through the identity chain:
```
CalendarVersion change → CalendarRef.version changes → view_hash changes → experiment_id changes
InstrumentSpec change → InstrumentSpecification.version changes → view_hash changes → experiment_id changes
PitCutoff change → PitView.pit_cutoff changes → view_hash changes → experiment_id changes
```

## PART 10: RED-TEAM SECURITY / TRUST BOUNDARY

### 10.1 Protection Definitions

| Threat | Protection Mechanism | Phase |
|--------|---------------------|-------|
| Lookahead bias | Chronological processing + PIT filtering + `LeakageDetector` (existing) | Phase 3 + 4A.1 |
| Future publication leakage | `PitViewBuilder.filter()` excludes `publication_time > pit_cutoff` | 4A.1 |
| Revision leakage | `RevisionChain` queried at PIT cutoff, only `revision_time <= T` visible | 4A.1 |
| Survivorship bias | `PointInTimeUniverse` tracks listing/delisting dates (later) | Later |
| Incorrect corporate-action history | Corporate actions create new `InstrumentSpecification` versions (later) | Later |
| Incorrect futures rollover | `RolloverPolicy` is explicit and deterministic (later) | Later |
| Calendar mismatch | `CalendarRef` with version, included in `view_hash` | 4A.1 |
| Timezone leakage | UTC normalization + naive datetime rejection | 4A.1 |
| Nondeterministic ordering | `TieBreakerPolicy` with deterministic serialization | 4A.1 |
| Wall-clock contamination | No wall-clock defaults in new schemas; `provider_timestamp` frozen as exception | 4A.1 |
| Mutable research artifacts | All PIT models frozen; append-only chains | 4A.1 |
| Synthetic data as real evidence | `EvidenceProvenance` label propagated to PIT views | Phase 3 + 4A.1 |

### 10.2 Integration with Existing Trust Models

**`EvidenceProvenance` (existing):** REAL, SYNTHETIC, SIMULATED, UNKNOWN. PIT views propagate the evidence provenance from the underlying dataset. `DataQualityGate` blocks SYNTHETIC and QUARANTINED datasets from downstream use (existing behavior, unchanged).

**`DataQualityGate` (existing):** Validates data quality before downstream processing. `PitViewValidator` runs after `DataQualityGate` to add temporal eligibility checks. No modification to `DataQualityGate`.

**`ProvenanceTracker` (existing):** Tracks dataset versions and provenance. `PitSidecar` references datasets by `dataset_id` + `dataset_version`, integrating with the existing provenance system.

**No conflicting parallel trust models.** The PIT trust model extends existing trust models; it does not replace or duplicate them.

### 10.3 Specific Leakage Prevention

1. **Future publication:** `PitViewBuilder.filter()` iterates all data items and excludes any with `publication_time > pit_cutoff`. This is silent exclusion, not an error (DD-03).
2. **Revision leakage:** `PitViewBuilder` queries `RevisionChain` and uses only revisions where `revision_time <= pit_cutoff`. The latest revision with `revision_time <= pit_cutoff` is the current value at the PIT view time.
3. **Corporate actions:** Corporate actions create new `InstrumentSpecification` versions effective from the action date. Historical data remains under the old specification. PIT views at time T use the `InstrumentSpecification` effective at T.
4. **Futures rollover:** `RolloverPolicy` is explicit and deterministic. Roll decisions use only information available at the PIT cutoff. Back-adjusted continuous series prices are never confused with raw contract prices.
5. **Calendar mismatch:** `CalendarRef` with `calendar_version` is included in `view_hash`. Different calendar versions produce different experiment identities.
6. **Timezone leakage:** All PIT timestamps are UTC-normalized. Source timezone is preserved as metadata on `Venue`, not embedded in timestamps.
7. **Nondeterministic ordering:** `TieBreakerPolicy` is declared and included in `view_hash`. Default tie-breaker is deterministic lexicographic ordering.

## PART 11: PHASE 3 COMPATIBILITY PROOF

### 11.1 Phase 3 BacktestEngine Remains Compatible

**Proof by design:** `PitViewBuilder` produces a filtered `Dataset` which is passed to the existing `BacktestEngine.run(strategy, dataset)` method. The `BacktestEngine` receives a `Dataset` and a `StrategySpec` — the same types it has always received. No modification to `BacktestEngine` is required. The backtest engine is completely agnostic to whether the dataset was PIT-filtered or not.

### 11.2 Existing Phase 3 Result Hashing Remains Unchanged

**Proof by design:** `BacktestProvenance.compute_result_hash()` is not modified. The `result_hash` formula remains: `sha256(strategy_hash|dataset_hash|canonical_trades|canonical_equity|canonical_metrics|config_hash)`. New `view_hash` and `experiment_id` use new method names (`compute_view_hash()`, `compute_experiment_id()`). Existing `result_hash` field continues to use the same formula with the same inputs. New fields (`view_hash`, `experiment_id`, `pit_cutoff`) are optional with default values.

### 11.3 Existing Phase 3 Datasets Remain Readable

**Proof by design:** `Dataset`, `Candle`, `Instrument`, `ProvenanceRecord`, `DatasetVersion` are not modified. `PitSidecar` is a new model referenced by `dataset_id` + `dataset_version`. Datasets without a `PitSidecar` are valid and receive a default sidecar. The `PitViewBuilder` handles both cases.

### 11.4 Existing Phase 3 Tests Remain Valid

**Proof by design:** No Phase 3 source file is modified. No Phase 3 test file is modified. All 464 existing tests continue to pass. New tests are added in new test files for new functionality. The `test_pit.py` tests (97 tests) continue to pass unchanged.

### 11.5 PIT Functionality Is Additive

**Proof by design:** All PIT components are new modules or new classes that do not modify existing code. `data_engine.pit` (v4.1.0) is already self-contained. `data_engine.multi_asset.temporal` (v4.0.0) extends it. `data_engine.multi_asset` (v4.0.0) adds PIT-aware research constructs. Existing imports and interfaces are preserved.

### 11.6 Legacy Behavior Is Not Silently Changed

**Proof by design:** Legacy datasets without `PitSidecar` records receive a default sidecar with implicit temporal metadata. The default behavior is equivalent to "all data was published at the dataset retrieval time." This is the same behavior as the existing Phase 3 backtest (which uses all data regardless of publication time). PIT filtering is opt-in — a `PitViewBuilder` must be explicitly invoked. Without explicit PIT construction, the backtest behaves identically to Phase 3.

6. **`ingestion_time` is excluded from all PIT eligibility calculations and hashes.**
7. **Future publication data is silently excluded from PIT views, not treated as an error.**
8. **Revision history is append-only.** Existing entries cannot be modified or deleted.

10. **No wall-clock time affects research identity or reproducibility.** All datetime fields must be explicitly provided.

13. **`view_hash` is distinct from `dataset_hash`.** Same dataset at different PIT cutoffs produces different `view_hash` values.
14. **`experiment_id` includes PIT snapshot hash, not just dataset hash.** Same dataset at different PIT cutoffs produces different `experiment_id` values.
15. **All evidence provenance labels (REAL, SYNTHETIC, SIMULATED, UNKNOWN) are propagated to PIT views.** SYNTHETIC and SIMULATED data must never be represented as REAL market evidence.
16. **`DataQualityGate` remains unchanged.** `PitViewValidator` runs after `DataQualityGate` and adds temporal eligibility checks.
17. **Corporate actions create new `InstrumentSpecification` versions, not data corrections.** Historical data remains under the old specification.
18. **Futures continuous series and individual dated contracts are distinct instruments.** They are never confused.
19. **Calendar version changes produce different experiment identities.** Calendar version is included in `view_hash` and `experiment_id`.
20. **No live trading, broker integration, real-money execution, or automated strategy optimization is implemented.** This is a research and paper-trading system only.
